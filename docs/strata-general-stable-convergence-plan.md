## 2. 三种状态：阻止放行不等于停止开发

每次 decision 分别记录候选资格、下一步动作和停止理由，避免一个 HOLD 包办一切。
这是记录约定，先复用现有 JSON/Markdown，不为此开发新的编排平台。

| 候选资格 | 开发动作 | 何时使用 |
| --- | --- | --- |
| `NOT_QUALIFIED` | `DIAGNOSE` / `IMPLEMENT` / `OFFLINE` | 新候选或已定位可修复问题；继续做当前分支 |
| `HOLD` | `COMPLETE_REGISTERED_BATCH` | 普通失败，仍有安全且有诊断价值的预登记配对；冻结版本继续 |
| `HOLD` | `REVISE` | 已有证据支持窄修复，旧批封存，另冻新候选 |
| `HOLD` | `DESIGN_REVIEW` | 相同问题反复无改善或修复相互冲突；按第6节分析后自主决定范围内下一步 |
| `PASS_STAGE` | `ADVANCE` | 满足本阶段固定门槛，进入下一阶段，不顺带开放扩展能力 |
| `CORE_STABLE_SCOPED` | `HANDOFF` | 全部核心门槛和产品流程通过，交付 release-ready，不自动发布 |
| `HOLD` | `PAUSE_EXTERNAL` / `PAUSE_USAGE` | 需要关键授权、外部条件或达到用户用量线 |

真正停止整个执行的条件：用户叫停；weekly 到线；核心 release-ready；必要外部
条件不可恢复；经过规定复盘后，剩余方案都需要改变模型、信任边界、权限、正确性
标准、产品范围，或没有可检验的范围内下一步。最后一种必须提交具体证据和选择，
不能只写“gate 没过”。发现安全故障立即停 live，但范围内离线诊断/修复可继续。

## 3. 执行主线与每阶段成功/失败出口

```text
接续核对
  → 版本引用窄修复 + 离线安全控制
  → 已知问题固定两格
  → 原三类兼容6格 + 六类保留任务12格
  → 四种错误起点修复
  → 冻结版本的新项目留出6格 + 安装/连续任务/恢复验证
  → 核心 release-ready

任一阶段普通失败 → 完成安全的固定诊断批 → 分类 → 窄修复或设计复盘
                 → 新候选 + 受影响回归 → 回到最早失效门槛
权限/安全/证据异常 → 停 live、离线定位；边界内修复可自主继续
```

### A. 接续与基线核对，0 live

1. 先 `Get-Location`；核对根目录及 DEV 的 branch/HEAD/dirty，实际 weekly、任务
   进程、写锁和模型驻留。未知锁先查所有者，不删除；已有批次先接续，不重复派工。
2. 读取第1节四批的 decision/handoff；按需看对应 request/response/检查和 diff，
   不扫描整个旧历史。核对当前91文件产品 hash 与 DEV 差异，保存本轮将改文件的
   前镜像/来源记录。用户旧改动不清理、不混入产品。
3. 复用现有精确计数器、版本绑定和隔离工作区。产品/安装或模型配置与记录不符时
   先定位漂移；不静默把漂移算新 baseline。模型未就绪按加载规则等待，不能换模型。
4. 新建阶段目录，记录 feature/unit/integration risk、合同ID、范围、依赖、假设、
   预算、后续固定格顺序及本计划版本。当前 stage 的旧 HOLD 保留为父证据。

成功：事实与开发源可追溯，进入 B。失败：可修复的路径/实验准备先修；未知用户
重叠改动或需要修改只读安装时才请求介入。不要重做已验证的 S0/S1/S2 全部工作。

### B. 首个候选：宿主拥有观察版本引用，先0 live

核心假设：保留精确编辑底座，移除长 hash 抄写可以减少无编辑的协议失败；这不
承诺修复模型语义能力。仅更换模型侧版本引用与必要错误反馈，不同时调预算/采样/
上下文/测试合同，也不新增 patch 方言或任意执行工具。

预期模型侧结构示例（字段名可在冻结前调整一次）：

```json
{"path":"src/example.py","version_ref":"v7","start_line":12,"content":"..."}
```

```json
{"changes":[{"path":"src/example.py","operation":"replace","version_ref":"v7","edits":[{"find":"旧块","replace":"新块"}]}]}
```

引用是宿主发出的不透明编号，只是版本关联；不是授权凭据，也不证明模型理解了
全部源码。宿主账本保留完整 hash、规范路径、task/合同/配置/运行时身份和版本。
模型引用短编号，宿主解析后仍交给同一精确 SafeEditor；不得模糊修补或回填当前 hash。

必须先明确并实现以下语义：

- 引用只随实际交给模型的 read/search 证据或有明确版本的源码投影发出；目录
  枚举和纯路径提示不产生“已读”证据。只授予原先批准范围内的操作。
- 同任务内路径+版本稳定映射；反复读同一版本不能制造新进展、重置 no-op 或补预算。
  仅搜索到路径但没有源码证据时不自动获得可编辑版本。
- 提交时核对 task/epoch、合同/config/runtime、批准路径、观察版本、当前完整 hash；
  提交前再次检查外部漂移。未知引用、跨文件/跨任务引用、过期引用均零写入拒绝。
- 格式化、成功编辑、外部变动使旧版本引用失效；新版本在实际交给模型后才能使用。
  创建文件仍走原 create 权限；创建成功后的后续编辑也需当前版本引用。
- 一批多文件必须全部预检，任何一项失败都不得应用其他文件。中断仍按现有日志/
  preimage 协调；不能把它宣传为 OS 原子事务。
- 压缩保留当前合法引用及其绑定，不能让旧引用复活；resume 采用明确保守规则：
  新 attempt 重新取证发引用，预算/旧事件不重置，未确认的写操作不得重放。
- 已拒绝且完全未改源的引用可否复用须在 schema 冻结前定死；建议版本仍匹配时
  可用于不同修正提案，仍受相同 no-op/协议预算约束。已应用提案不能重复应用。
- 失败反馈区分 malformed/unknown、stale、path/task mismatch 和 exact-block miss；
  返回真实原因与合法重读路径，不给猜测的实现答案，不自动把错误引用“修正成功”。
- 旧完整 hash 协议如保留，只供明确旧 profile；新 profile 不同时给模型两套选择。
  产品默认关闭，archive 继续保留完整 hash，不改既有验收/handoff 意义。

单元风险为 high：拥有 `VERSION_BINDING`、`SCOPE_BOUNDARY`、`NO_PARTIAL_APPLY`；
依赖现有 `TASK_BUDGET`、`CURRENT_CHECKS`、`EVIDENCE_HISTORY`。Primary 全量审查变更。
不要为了缩短引用去重写共享 WorkerRuntime 或删除旧安全层。

离线门槛必须覆盖真实工具 schema→wire→宿主→编辑器，而不只测 Python 小函数：

| 控制组 | 必须观察到的行为 |
| --- | --- |
| 正常生命周期 | 读→提案→格式化→完整检查→submit；多文件、create 后再编辑均可达 |
| 负控版本/身份 | 未知/猜错引用、旧引用、跨任务/路径/epoch、外部漂移、重复已应用提案均拒绝且不写 |
| 边界/事务 | 保护文件、reparse/路径别名、越权、重复路径、非唯一替换、混合有效/无效批保持原保护 |
| 状态/恢复 | 压缩后绑定未丢；restart/resume 不补额、不重放未知写入；格式化新版本必须重新绑定 |
| 检查/交接 | 初始绿色不结束；0测试/漏检查/缺必需测试/旧绿色不能交接；每次有效编辑都有全套写后检查 |
| 历史错误重放 | 旧58字符请求在旧协议仍拒绝；新接口用合法观察引用能通过版本预检，坏引用仍拒绝 |

最后一项是协议控制，不能把机械转换的旧模型输出算作新的模型成功。
精确 token counter 保持启用，schema 变更后在相同已安装模板上重放实际输入，确认
工具封装/计数/恢复可达；不改 Strata 安装，不将纯编码计数算推理。

成功：冻结新产品、schema、检查证据和兼容性映射，进入 C。
失败：离线复现后窄修；涉及已冻结修改则另版本。没有安全等价证明不启动 live。
同一绑定设计两次离线修复仍暴露互相矛盾的不变量，进入第6节设计复盘。

### C. 固定两格验证已知问题，不重新抽样补成功

先登记2个独立 finite-json 起点，使用 coverage 批次相同的已增强保护测试、合同、
依赖和预算。唯一实质变量是新版本引用协议。两格都是已暴露回归，不是新题。
两格均独立运行，同一任务内部可以正常修复；不把第一格失败后临时教给第二格。

门槛仍2/2独立完整接受、0边界违反。分别记录“能否有效应用编辑”和“代码是否
正确”：通过前者不能替代后者。模型不再抄 hash 但改错代码，应转语义/覆盖分支。

- 2/2：进入 D。登记为当前已知机械阻塞已解除的证据，不能声称通用稳定。
- 1/2或0/2：普通失败完成固定两格后封存，按第5节归因；范围内可修问题继续修。
  不能通过加第三格将1/2变成2/2，也不以旧正确补丁代做失败格。
- 相同引用问题复发：核对实际 SSE、映射和反馈；不得默认模型仍抄错。若编号过于
  易混淆，可在新候选改唯一表示；不加多种容错映射或自动猜最新版本。
- 若正确版本预检已工作但新的语义错误被检查拦住，版本假设可记 supported，
  整体候选仍 HOLD，下一轮针对实际错误，不撤销已证明有用的版本保护设计。

失败：只回到最早受影响层；修协议/上下文这种全局路径后需重验当前6和12，不能
借用旧版本模型成绩冒称新版本合格。仅单题可信检查补缺且 runtime/其他输入完全
一致时，可保留不受影响格；必须列出具体 pins 和失效范围，失败记录不消失。

### E. 四种错误起点：确认有界修复能力

复用 `DEV/.checks/repair-task-preparation-1` 的离线准备作为来源，不直接当可执行
live 注册。静态错误、漏 await、跨文件字段未贯通、UTC语义回归各1格，固定4格。
每个初始错误都必须有真实、可理解的既有检查失败，范围内存在合规修法；不得给
参考补丁。这测给定错误起点的修复，与自然自犯错后的恢复分别统计。

开跑前修正实验适配器的潜在假失败：当前 `supplemental_control.py` 按普通任务
族恢复旧函数；async 的错误实际在 `ToolRegistry.invoke`，crossfile 在 logging
formatter，原 targets 不对应这两种故障。先注册逐格真实故障靶点，在好/坏草稿
上证明检查能区分；不能把注入没有改变源码、收集错误或无关旧函数当模型失败。
finite-json 起点沿用增强兼容保护，保护测试/参考仍与 Worker 可写范围隔离。

门槛≥3/4独立接受、0不安全/过期/漏检查接受；失败格保留。每格完整检查必须运行，
不得只执行最近失败测试。代码被检查正确拦住不等于该格成功，但可以区分安全退回。

- 通过且无已知系统性未解决缺陷：进入 F。
- 未通过但有有效编辑→错误收敛：分析真实余额与反馈可达性；先找宿主遗漏或
  定位缺失，不自动扩请求。需改变预算时按第6节登记新对照，旧成绩不改。
- 重复相同语义错误、反馈准确且有余额：转有限能力/任务表述诊断；不继续无限
  few-shot、咨询者或 Primary 教算法。没有可检验改进时属于需要关键判断的结论。
- 模型只修测试或删行为让绿：Primary拒绝；检查补强和语义失败分别记录。

### F. 新项目留出与核心产品流程

只有 D/E 当前有效资格成立才能准备此批。冻结产品后从未用于当前候选调参的
材料选3个任务，覆盖局部功能、行为保留、跨文件依赖，各2次，共6格。至少两个
可信项目来源；优先现有依赖环境、真实代码切片，不新增 Docker/依赖迁就题目。
这批是当前版本真正的迁移依据，不能把 finite-json 改名字再当新题。

先做独立参考可行性和原始失败/环境控制；保护测试及隐藏终验在 Worker 范围外，
只读公开测试可以提供。登记合同中相互影响的行为要求；Primary不给算法/顺序提示。
至少包含同一安装上的任务依赖链：第二项绑定前项被接受的输出。若前项失败，
后项记 NOT_RUN_DEPENDENCY，本批不完整、不能 PASS；不得手工代修前项后称自主链。

门槛保持≥5/6、每组≥1/2、全部6格有有效执行结果、0安全/证据违反，所有最终
接受单元逐项满足合同。普通失败完成剩余可独立运行格；不为凑分加任务。

同步做产品流程（尽量离线或复用6格，不额外堆 live）：

- 最终冻结 ZIP 在新路径安装；文件/版本/pins正确，无实验源码隐式依赖。
- 同安装顺序任务、已验收结果成为下项起点、已有未提交修改保留。
- status只读；取消只影响任务自有进程；重启不补预算；旧版本/未知请求正确拒绝。
- export 带 patch/preimages/checks 和冲突预检，不自动改真实工作树或 Git。
- 实际 CLI/示例/用户文档一致，产品包不含开发计划和完整历史；旧 preview 保留。

通过：`CORE_STABLE_SCOPED`/release-ready，给用户候选、证据、已测范围与限制；停止
本轮开发，不自动 commit/push、发布或实施 S5/S6。
失败：根据第5节修复。若看过留出结果后改 runtime/提示/预算/任务相关算法，旧题
永久转回归；修复后须新的封存留出，不能反复同题通过后仍叫未知迁移。
仅包内用户文档错误且无 runtime/config 行为改变，可只复验安装/文档对应控制。

首个新候选沿用 `strata-unit-v1`，不因抄 hash 失败顺便加额度：

| 编辑/完整检查 | 有效变更集≤4；起点检查1独立，写后全检查≤4，与每次有效编辑配对 |
| 格式化/协议恢复 | 准备≤6；协议/传输恢复共≤2；无实际改动不算有效编辑 |

| 时间 | 任务活跃总1800秒；请求≤600秒；单检查≤180秒且受任务剩余时间约束 |
| token预检 | 纯计数≤18次/任务、每次≤15秒，计入1800秒；不算实际模型请求 |
| 驻留等待 | 就绪等待≤900秒、约10秒探测；不发推理、不自动reload，独立记录冷加载 |

以真实代码 LIMITS/profile/pins 为准核对差异，不能只传 CLI 的 `--weekly-used`
就声称完成用量核对。每格前与开发阶段后读取实际 weekly；达到50%停止新增派工，
安全收尾已启动任务，不突然丢弃记录。读数不可观测则重读，持续不可用暂停新 live。
长本地调用轮询同一会话，不能因 shell yield 另开 Worker；保持可见进度更新。

单候选无返工路线最多30格（C2+D18+E4+F6）；严格预登记共享两格时28格。
按每格30分钟上限是15/14小时活跃本地执行上界，不是预计时间或“必须花完额度”。
普通失败后的新候选也要重新登记新增 live 数量和预计最大时间；禁止隐藏补跑。
长期开发由 weekly 控制，各任务仍有上述硬限，不能换 task_id 给同格充值。

## 5. 按最早偏离点选择修复分支

| 真实观察 | 分类与先做什么 | 可以自主采取的下一步 / 不可混淆之处 |

## 6. 什么时候复盘，什么时候自动改计划

### 6.1 每格与每批做多深的分析

每格完成：写5–10行或紧凑JSON，记录实际状态、最早偏离、编辑/修复/请求、Primary
介入、是否影响剩余固定格及下一动作。成功只作必要终验，不重新研究架构。

每个固定批结束：汇总所有格、分组门槛、错误放行/误拒/NOT_RUN、候选资格与下一
分支。输出 decision/handoff 后继续已允许分支；写总结本身不代表要结束开发。

立即专项分析：绿色错误草稿、安全/版本/检查不变量失效、同一修复带回旧故障、
raw wire与宿主解释不一致。普通语法/测试错误先让Worker用原预算修，不逐错改harness。

### 6.2 无进展复盘阈值不是“再次让用户批准继续”

下列任一成立必须先做设计复盘，暂停新增同假设 live：

1. 同一稳定失败签名在两个已完成的**不同候选周期**中没有可核查改善。
2. 同一工作单元三次连续同类无进展/质量门槛失败（沿用仓库策略）；预登记配对
   仍受安全和继续规则限制，不借“诊断”启动更多相同格。
3. 修A坏B、修B又坏A：第一次确认即画出冲突的不变量，不先回滚来回抽模型。
4. 一个开发区间累计 weekly 增加5个百分点仍没有关闭阻塞或进入下一阶段。

weekly 是账号共享观测；第4项只触发检查工作价值，不能把其他任务的用量归给本实验。

失败签名固定为“层+违反合同+触发条件”，不能换批次名/题目名清零。
“进展”指离线可重放故障被消除、原阻塞可达且无退化、有效修复链出现或前置
资格确实推进；只有更高随机通过率或改报错措辞不够。

复盘只产出一页决策和必要附证：

- 当前前三个阻塞、各自最早偏离及反证；此前假设为何被支持/否定。
- 比较保留当前设计、改一个机械接口、修实验/证据、待能力判断这几个具体选项。
- 下一步要区分的一个假设；最少离线控制、受影响面、保留回归和预计费用。
- 判断是否仍在用户授权范围；选择继续/撤销当前候选/关键决策交接，并说明原因。

优先用现成 request/response/check/diff 重放；若仅靠离线不能区分，允许登记一个
最多4格的已暴露诊断对照（最多两种处理，各2格），同模型同安全标准。诊断不赋予
发布资格，不覆写原失败，保持任务预算；不能每复盘都机械加4格。诊断后立即结论。

复盘有不同、可检验且范围内的机制改进：自动修改未来计划和 registration，继续
离线→窄回归→失效门槛。没有新证据不能无限命名第三/第四候选重复同一招。
只有需要新外部条件/关键边界选择，或无可执行且可证伪的方案时，才停止并找用户。

### 6.3 自动修订计划的边界

执行者可自主更改：未开跑阶段的依赖顺序、真实发现的适配器错误、负控覆盖、
单一机械接口实现、同合同的可信检查缺口、结果记录和受影响回归范围。先写改动
理由、证据、保留不变量、失效证据、后续固定批，再实施；不得事后改已开跑批。

预算调整不是默认动作。若重放证明每次有效编辑没有对应完整检查机会，先修
调度实现。若机会已对齐但资源仍是可证实瓶颈，单独登记诊断profile：一次只检验
一个资源假设，同模型同验收，必须有最坏轨迹离线重放。整数资源向下取整后的
上限不得超过第4节原值的125%，不允许逐版本复利增加；一次复盘至多一个对照。
有效编辑与对应完整检查是不可拆开的资源对，若调整须一起登记；请求/工具/时间/
累计输出之间也须验证可达性，不能只提高一个数字制造无法使用的额度。
它不自动成为正式profile；作为正式候选必须重新资格验证，旧分数不改。
上下文、单次/累计输出、模型并发、协议恢复和安全/无进展停止不在此自动增加范围；
更大改变属于关键决策。首轮版本引用候选明确不调整任何预算。

必须用户判断：换模型/后端/量化、扩大信任边界或任意执行、修改只读安装/兄弟
仓库、移除检查/降低正确性门槛、缩小用户要求的产品目标以宣布成功、进入S5/S6、
commit/push/发布、提高用户usage停止线。普通代码修复不属于上述关键决定。

## 7. 防止“修来修去”和成绩混用

每个修复都留下最小确定性反例及对应正控，组成保留控制集；新候选必须通过其
触及的既有反例，才能跑 live。保留精确token预检、压缩状态、版本/路径/预算、
完整检查/交接、default=str兼容、补充测试执行等已确认不变量。

| 变更类型 | 哪些证据失效/需要复验 |
| --- | --- |
| 只改开发文档/统计显示 | 对应静态核对；不能凭它改变原运行成绩 |
| 单题测试/实验适配器修复，产品与其他输入相同 | 原错误/正确草稿离线控制+受影响格新批；未受影响格逐项pins复用 |
| 工具schema、编辑、预算、上下文、准备器或模型可见指令改变 | 当前产品相关离线全边界；兼容6、保留12及修复4重新取得有效资格 |
| 安全/归档/交接语义改变 | 所有受影响安全负控，实际完整链及安装/恢复控制；不以“没改模型”豁免 |
| 看过F的结果后改候选 | 旧留出转回归；新的冻结材料用于最终迁移资格 |

旧产品/旧批绝不改字节。开发修复不合格时，可在 DEV 撤销**明确属于本次的**改动
或另建候选；先保留diff/检查，不 broad reset、不覆盖用户原改动。若新修复损害
已通过不变量，该候选不能作为下一版本基线，先定位相互作用。

阶段总体通过不合并候选A的成功格与候选B的成功格凑数。相同产品与未变输入的
有限复用要显式列出，避免每个小文档修正重跑全部，也避免偷换验证版本。
历史失败永远可见；重复题累计通过次数不是独立泛化样本。

## 8. 每批产物与成本

复用现有独占创建的实验工具，不建立新平台。每个阶段/候选至少有：

- `registration.json`：父批、假设/变量、候选/schema/check/model pins、固定顺序、
  exposure、预算、门槛、普通失败继续规则、安全停止、实际weekly观测。
- `offline-controls.json`、`candidate-pins.json` 或现有等价文件：读写/版本/检查/
  包内容控制，正负参考结果；重用证据必须给路径与hash。
- 每格原request/response/events、preimages/diff、全部检查、独立验收和disposition。
- `metrics.json`、`decision.json`、`handoff.md`：数量、资格、未运行原因、下一动作。
- 需要修订时追加 `plan-amendment-<N>.md/json`；不要改闭合registration。

决策至少包含：candidate_id、eligibility、next_action、earliest_failure、
root_cause_confidence、evidence_paths、invalidated_evidence、next_gate、weekly_used、
stop_reason。可保留现有status同时补充这些语义，不强制批量迁移旧JSON。

成本分三层记录：一次性harness研发/题库准备；每任务合同与测试/定位/协调；最终
审查与独立验收。记录实际HTTP、读取、有效编辑、协议恢复、no-op、当前失败/已解/
新退化、检查拦截、wrong-ready、最终错误接受、assisted/接管、NOT_RUN、加载/运行/
检查时间。没有可靠测量写unknown，不从weekly差值推算精确云token或节省百分比。

Primary 提前给具体算法、运行中解释新边界、手找原来没给的依赖、代写修复都单列。
独立隐藏验收失败不能作为同一自主格的修复提示；后续暴露回归可提前披露已确认
合同测试，但记录暴露状态。宿主正确拦截和最终独立接受是两个指标。

发布依据仍需Primary全量审查，不宣称已降低这部分成本。通用稳定核心通过后可
为后续成本实验留下清晰基线；目前不自动启动Primary-only对照或新常驻角色。

## 9. 最终交接必须回答

1. 当前哪个冻结产品可用；是否达到核心资格、仍需哪些Primary职责。
2. 兼容6、保留12、修复4、新留出6各自实际结果；共享格只算一次，失败原样保留。
3. 是否还存在已知wrong-ready缺口、系统性机械失败、过期证据/漏检查接受。
4. 任务能否自主定位→多文件改动→自测→有界修复→交接；哪些恢复是生产语义，
   哪些只是自写测试/格式问题；被预算拦住的具体原因。
5. 安装、连续任务、取消/resume/export和已有dirty处理是否真实验过。
6. Primary反复工作是否减少有证据；未知成本和小样本限制是什么。
7. 若仍HOLD，写下可执行下一分支或需要用户选择的具体设计问题；不能只有“未达标”。

## 10. 给接手模型的执行提示词

> 按 `docs/strata-general-stable-convergence-plan.md` 推进 Strata 通用稳定核心，
> 结合原 `docs/strata-general-stable-plan.md` 的产品范围，先读最新 progress 与
> canonical decision/handoff。先运行Get-Location，核对Git/dirty、实际weekly used、
> 在跑任务和单模型驻留，复用现有DEV。先做宿主版本引用的窄修复与真实链路离线
> 负控，再按固定两格、兼容/保留矩阵、错误起点修复、新项目留出和产品流程推进。
> 保持iq3_s、单驻留、兄弟仓库/Strata安装只读，保留所有历史及现有改动，不改生产
> 默认、不commit/push、不实施S5/S6。weekly used上限50%，后续用户更新优先。
> 普通失败按计划分类、复盘、修订未来候选并继续，不因单个gate HOLD或已写handoff
> 就停止开发；不要放宽正确性、补跑抹失败或重置任务预算。同一假设连续无进展先
