## 3. 查证结果与证据等级

### 3.1 已确认的运行时问题：优先修复

**F1：失败基线消耗实现后的修复额度。**

`worker-runtime.py` 的 system prompt 要求新任务首次编辑前运行 VALIDATE。失败验证设置 `pending_failed_validation=True`；`_record_edit()` 在该状态下将下一次编辑计入 `repairs`。内存诊断确认：初始 `repairs=0`、`edit_revision=0`、失败基线状态后首次编辑得到 `repair_count=1`。因此默认两次 repair 中，首次实现已经占去一次。

这证明计数语义混淆；不证明增加可用机会就能修好所有语义缺陷。应修计数语义并重新测量，而不是全局加大限制。

**F2：诊断执行前要求声明顺序约束已经满足。**

`validate()` 在运行命令前调用 `_contract_check()`。包含顺序约束的 packet 必须提交 `required_order_confirmed=true`；包含禁止顺序的 packet 必须提交 `forbidden_orderings_absent=true`。内存诊断确认：如实报告顺序尚未满足会在测试执行前被拒绝。这与诊断原始缺陷或未完成草稿的目的冲突。

模型填写的布尔值不是语义证明；仍需保留真实验证与提交门槛。将诊断和最终声明分离，不等于降低最终验收。

实现入口：`.local-agents/worker-runtime.py` 中 `system_prompt`、`validate`、`_contract_check`、`_record_edit`、`_begin_edit`、终态及 handoff 校验；不要依赖易变行号。

## 4. 阶段 A：先修诊断与验收状态语义

Primary 直接处理状态机、兼容性与 gate 判断，避免让本地 Coder 决定安全边界。feature/unit/integration 风险均按 high；拥有 `diagnostic-not-acceptance`、`repair-budget-accounting`、`fresh-validation-handoff` 契约。按 cohesive unit 分开补丁与验证，完成 A 后再做 B。

### A1. 基线与修复预算

目标语义：

- 新任务在首次成功源码编辑前的诊断不消耗“初次实现后的修复”额度。
- 首次实现后真实验证失败，后续有效编辑开始一个修复周期；同一周期内多文件/多次编辑不被算作多个周期。
- 无效动作、no-op、失败替换不被伪装成有效修复或进展；次数、时限、协议错误仍独立有界。
- 基线故障仍保留失败证据和来源；不能通过重标为 baseline 重置已开始的修复周期。
- 继承 rework 使用父档案及当前哈希判断证据是否仍有效。不得仅因新 run_id 把已修改草稿伪装成从未编辑的初始状态；明确每次调用额度与任务级 streak 的区别。

验收必须覆盖：失败基线后首次编辑、后续两个修复周期、同周期多次编辑、no-op/替换失败、多次 baseline 验证、编辑后的失败验证、继承与哈希漂移，以及限额到达后拒绝继续写入。

### A2. 诊断允许失败；提交必须有证据

目标语义：

- 诊断/check 应能运行尚未满足顺序或行为契约的代码，允许如实报告 unmet/unknown。不能要求模型为了获得测试结果而先声称所有条件满足。
- 合法、已授权的诊断命令可执行，不代表其运行结果能直接进入 handoff。命令白名单、读写范围、保护测试和配置来源不改变。
- 模型 acknowledgement 与 runtime 验证事实分开存储，不将缺失或 false 自动填成 verified。
- 最终提交仍要求当前输入的有效测试、静态检查、必要契约处理以及现有身份/归属 gate。任何诊断放宽都不得导致旧验证或未验证草稿被接受。
- 明确 `check`、`final`、`FINISH_SUCCESS` 的兼容语义。保留现有 schema-v1/v2 正常用户路径；若旧版“通过 check 后显式 FINISH_SUCCESS”继续支持，提交时必须重新检查完整 eligibility。

关键反例：原始代码已绿色但目标尚未实现；顺序不满足但需要运行诊断；合法 false/unknown 声明；伪造通过字段；零测试、全跳过、缺 JUnit；验证后编辑/输入漂移；旧档案和新 run 混用；final 后非法动作；基线耗尽预算；异常退出后部分修改。

先用模拟客户端和真实小 fixture 复现，修正后用少量真实模型确认协议可用。不要用模型偶然填 true 来证明 A2 正确。

**阶段 A 出口：** 上述反例回归通过，实际兼容路径可用，独立审查确认 handoff 未放宽，形成新冻结快照和变更归因。失败则继续确定性修复，不启动能力大样本。

## 5. 阶段 B：受控验证协议与修复表达

阶段 A 冻结版本成为新共同基线。旧 ov1/fm1 仅作历史，不能拿不同状态机预算的成绩直接归因于新提示。

先审计模型可见协议：哪些是模型需要判断的语义，哪些是 runtime 能确定的 bookkeeping。候选例子包括 runtime 枚举应检查的契约 ID、用已观察版本生成编辑引用、将失败状态与提交声明分开。版本引用必须仍绑定具体观察和当前文件内容，不能替模型无条件使用最新哈希。

每次只选择一个实验轴：

1. **协议简化候选**：模型可见字段更少，后端保持同一安全与验收规则。
2. **修复分析候选**：编辑前给出简短、可核查的失败假设、关联契约、源位置和需保留行为。它是待检验的输出，不是额外权威，不自动算进展。

不要同时改模型、采样、上下文保留、轮数、编辑工具、few-shot 和 gate。不要直接增加一个永久 Planner 或让 Coordinator 承担未资格化的语义判断。

如使用修复分析候选，单独评分其因果解释、契约关联和可执行性，再记录最终代码结果。分析正确但编辑失败、分析错误但碰巧过测试，都分别保留。分析时间和 tokens 计入总成本；不能把分析调用藏在 Coder 分母外。

runtime 对诊断的推断必须标为候选；不可根据测试名猜业务字段或自动生成“正确答案”。原始错误消息与受保护断言都需保留来源，不能把观察到的异常当作期望异常。

**实验预算：** 每个候选在两个开发问题族各跑两次，与同版本基线配对，最多 8 个 Coder 调用（自动 Reviewer 另计）。只有出现可复核进展才允许一次候选修订；最多两个候选版本。此为本批实验资源分配，不是产品层 task 调用硬上限。

**阶段 B 出口：** 协议安全与状态回归通过；候选至少显示一致的协议负担降低或自主完成改善，且无已观察到的安全/确定性回退，才进入未见题验收。小样本的同分或互有胜负记 inconclusive；没有改善则保留 A 修复，结束该候选，形成能力/范围决策，不再继续追加泛化提醒。

## 6. 阶段 C：冻结能力验收与成本对照

### C1. 冻结约 6–8 个独立任务

先完成开发调优，再冻结验收题。至少包括：

- 两个简单局部修改/定位任务。
- 两个含独立分支、不变式或错误路径的语义任务。
- 两个跨文件或两个依赖单元的集成任务；原子事务不得为降低风险拆开。

6 题为最小批次；最多 8 题，增加须在首次模型调用前登记理由。每题包含独立初始快照、正常/错误/边界验收、参考实现、能被验收拒绝的错误变体、模型不可读的 oracle、风险和 scope。既有 overlay/cancel/lock/retry 等已暴露题只作开发题，不重新命名为未见题。

**允许新增 complex testcase。** 接手 Primary 可在已授权范围和预算内自主补充复杂案例，无需逐题询问。新增理由应是覆盖真实使用中的未测交互或复现新失败模式；用可观察契约说明复杂性，不能只靠增加文件数、代码长度或人为障碍。

优先考虑这些场景：

- 一个用户目标跨配置解析、业务处理、结果输出，验证同一输入形式的端到端兼容。
- 多个依赖单元协作，局部测试通过但集成契约可能失败。
- 异步数据库聚合、事务完成、异常清理与取消的组合，明确行为边界并保持原子不变式在同一单元。
- 缓存、可变数据隔离、版本失效或并发交错；并发测试需可控调度，避免依赖碰运气的等待。
- Coder 修复一个错误后可能破坏另一个已通过行为，以及普通测试通过但 Reviewer 应发现的隐藏缺陷。

新增题按用途管理：开发诊断题可随新证据添加，模型调用仍计入阶段 B 的预登记资源分配和总 usage；确定性回归可按实际修复补充。未见验收题必须在候选开发完成后冻结，计入本批 6–8 题，不能使用已调优案例的换名版本。开跑后发现的新复杂场景另存为下一批或独立挑战，保持本批分母和原始成绩不变。

若新案例暴露权限逃逸、陈旧验证接受或当前承诺范围内的真实契约缺陷，必须阻止相应能力放行并单列证据；不能以“已冻结”为由忽略。超出当前承诺范围的新能力记为扩展需求，不自动把所有新题变成当前版本的新增 release gate。新增题不会授权改动只读兄弟仓库、安装依赖、扩大模型权限或启用 Coordinator；先在 kit 内验证依赖可用、参考实现通过、错误变体失败及可重复性。

保证至少两个题实际需要 Explorer 定位；每次只问一个具体问题，单独评分路径/行证据、真实读取与结论是否回答问题。无需定位的题记 N/A。本批不强行让所有题经过所有角色。

任务、参考答案、测试和成本口径均在首调用前冻结。每题两次独立本地执行；每次 fresh workspace、unique run_id。基线与候选比较应使用相同输入与预算，交错执行顺序，记录模型配置、加载、上下文占用、请求大小和实际角色调用。不得在一轮中途修改题目或参考答案。

对于未见题，Primary 提供具体修复语义即转为 guided recovery，原自主成绩固定为原结果。恢复可继续用于诊断，不能补回自主通过率。题目确有歧义时保留并标为 fixture/contract defect，创建新版本重新登记，不删掉旧失败。

### C2. Reviewer 使用独立 hidden/clean 对照

至少两个问题族，每族一份普通验证能通过的缺陷实现和一份合法实现。两轮重复共 8 次 Reviewer 调用。外部 oracle 必须区分 hidden/clean，且不能进入 Reviewer 可读范围。

报告分别记录：协议有效、引用有效、判定方向、因果解释有效、建议符合契约、正确实现误报。关键词 `structural_outcome` 只作筛查；`effective_detection` 需独立的 source/oracle 支撑和 Primary 判定。对精确判断拿不准就记未确定，不能自动通过。

自动 Coder→Reviewer 仍保留。独立挑战不是 Coder 成功，不计完整 feature 接受。

### C3. Primary 直接完成的成本基线

至少为最小六题各建立一份 Primary-only 隔离执行记录，使用相同任务、保护验收和可用资料。指定顺序/匹配方式，记录任务熟悉度，避免将已看过参考答案的 Primary 执行当作盲测。

每个条件记录：

- 最终是否达到同一验收标准；人工接管、修复提示次数与内容层级。
- Primary 主动耗时、检查文件/hunk 数、主要工具调用、是否亲自给出关键算法或写实现。
- 本地模型加载、推理、验证耗时及端到端时间；成功与失败均计入。
- 可可靠取得的云端输入/输出 tokens 或费用；不可取得则明确 unknown。账户 weekly 百分比只作预算控制，不能冒充单任务成本。
- 每个接受单元的总协调成本；不能只比较成功的局部模型调用。

执行前在本批 manifest 冻结效率阈值，不能看结果后选择指标。建议暂以“同等质量、Primary 主动投入中位数至少降低 20%、无新增严重质量缺口”为有限效率试点条件；这只是本计划的拟定操作阈值，非统计证明或现有发布 gate 替代。测不准主动投入则不能宣布效率达标。本地可接受时长按用户已接受的慢加载事实记录分布，不擅自新增硬性 SLA。

## 7. Gate 与结束决策

| 维度 | 必要证据 | 失败时的处理 |
| --- | --- | --- |
| 安全与状态正确性 | A 的反例、身份/范围/保护测试/新鲜度/终态回归全部通过 | 阻止候选资格；不靠模型成功抵消 |
| 自主完成能力 | 冻结逐题两轮结果，单列初次通过、同调用修复、Primary 指导和接管 | 不把 guided recovery 算自主成功；按问题族报告能力边界 |
| Reviewer 有效性 | hidden 因果解释成立、clean 不误报，不能仅协议/关键词通过 | 未验证问题族继续由 Primary 承担对应语义审查 |
| 效率 | 同等验收的 Primary-only 对照与预登记成本口径 | 记未证明节省，不扩大默认委派 |
| 完整协作 | 至少一个真实定位、受控执行、Coder、Reviewer、Primary 和多单元集成链路两轮通过 | 单角色或单单元成绩不顶替完整链路 |
| v2.1 发布 | 逐项映射现有发布 gate，所有缺口有证据状态 | 本文结束不等于 v2.1 自动 GO |

本批的保守能力试点判定：只有每个纳入承诺的题两轮均经规定流程接受、对应 Reviewer 挑战合格、安全 gate 全过，才建议该**明确任务集合**进入限定试用；仍不能外推到整个语言/业务领域。若要缩减承诺范围，先报告完整失败分布并提出下一版预登记方案，不从当前分母删失败后宣告通过。

结束必须选择以下结果之一：

1. **限定能力可进入下一步资格验证**：列明任务范围、模型配置、风险上限、人工职责与未满足发布项。
2. **能力可用但效率未证明**：保留手动工具，不扩大自动委派。
3. **候选没有收益或持续失败**：停止该设计方向，提出范围收缩、模型适配或架构替代的证据化建议。
4. **预算/环境阻断**：保留已完成分母和 pending 项，不宣布能力结论。

完成 A 后，B 最多两个候选；C 一次预登记验收及必要的隔离确认。不得因新题失败无限追加 prompt、case、gate 或轮次。预算尚有余量不要求用完。另一方面，单次格式错误或某个小样本负结果不必结束整个已授权阶段；能在当前范围修正的实施问题继续完成并验证。

## 8. 回归与历史保护

修改前冻结当前 dirty workspace，而非仅 HEAD；记录相关文件哈希、分支、模型配置及已有进程/写锁。不要广泛 stash、reset、checkout 或删除旧结果。

按实际改动先跑针对性测试，再跑必要完整回归；状态机和提交边界属于必须覆盖完整回归的变更。自动化修改文件使用正常补丁工具，格式化工具只作用于本次相关文件。

`UNIQUE` 是必须替换的新批次标识。benchmarks/tests 的改动还应遵守它们现有 Ruff 配置。不要将一串命令的最后退出码当作所有检查通过；分别记录结果。

两项排除的历史原因是外部冻结来源漂移：

- `test_static_fixture_baseline_is_lint_only`
- `test_sample_identity_protected_metadata_boundary`

每份结果必须披露排除项。真正放行前，在 kit 内恢复/重建正确隔离来源并执行对应检查，或保持相关 gate 未满足；禁止修改只读兄弟仓库或直接改 pins 消掉失败。

## 9. 执行交接与最终交付

接手者首批工作：

1. 读 AGENTS.md、本文件及相关旧计划；确认当前用户授权与停止线。
2. `Get-Location`、Git 状态、实际 usage、解释器、LM Studio 与单模型配置检查。
3. 核对第 3 节证据，冻结当前基线和待改文件；保留旧档案。
4. 分别写出 F1/F2 的失败回归，再按阶段 A 实现与验证。先完成它们，再决定 B 的具体实验轴。
5. 每批登记目的、假设、固定变量、变更轴、判定口径、风险/契约、资源分配和失败后的分支；记录实际进度与剩余工作，无需逐步向用户确认正常实现选择。

正常入口仍是 `local-unit.ps1`/`local-unit.py`；成功后自动 Reviewer，Primary 决策用 `record-review.py` 写不可变记录。实验 synthetic Reviewer 档案保持 synthetic 标记。不要手写接受字段到旧 summary。

最终交付必须包含：

- F1/F2 的复现、修复语义、兼容与回归证据。
- 基线/候选/有指导恢复/接管/基础设施分别统计的结果；阶段未执行则标明。
- Explorer、Coder、Reviewer、Coordinator 实际参与情况与各自分母。
- 自主能力、审查有效性和效率三个独立结论；无法测量的项目明确 unknown。
- 支持的任务范围、人工职责、实际成本、现有 v2.1 gate 的逐项状态。

执行重点：**先让诊断与验收语义自洽，再测协议是否降低负担，最后用固定能力范围和实际成本决定产品去向。**
