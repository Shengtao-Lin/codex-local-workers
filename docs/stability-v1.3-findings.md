## 新的关键证据

失败分析候选的取消题第一轮通过了保护测试、静态检查、自动 Reviewer 和 Primary 高风险完整审查。这是真实的自主单元成功，但不能证明该问题族稳定。

第二轮模型错误地认为原有 bare `raise` 不保留异常对象，围绕错误因果解释修改了异常绑定和重抛，却未处理真正的取消捕获边界。给出真实源码、错误消息和合法契约 ID，并不保证语义诊断正确。

递归覆盖中，模型能正确指出浅拷贝造成输入别名，却仍生成 no-op 或不合协议的编辑。正确诊断与有效编辑是两个独立能力。强制分析字段也带来了额外拒绝，不能仅凭文字更完整就认定稳定性提高。

七份分析逐条按真实编辑前源码、关联验证和保护断言核查；只有一份在五项局部分析指标上全部有效，而其后编辑仍失败。评分不是盲评，状态可见，因此仅作为诊断证据；不以关键词或最终测试结果替代分析质量。

第二批 Coder 最大报告上下文占用约 54%，没有上下文超限拒绝。当前证据不支持靠增大上下文或轮数解决这些失败；也不排除其他任务中的上下文影响。

## 建议的产品边界

保留阶段 A 和历史限定定位资格，继续使用手动、边界明确的工具；复杂语义任务暂不作为稳定自主实现承诺。Primary 仍负责关键设计、保护验收和最终接受。能力相近的模型能否替换，需执行同一资格协议，不能仅凭模型名称或一次成功判断。

不要再追加第三个同类提示候选，也不启动阶段 C 未见题大批次。下一步应由用户决定是否采用较窄的产品承诺：Explorer 做证据定位；Coder 执行已明确的实现单元；Reviewer 提供独立意见，尚未资格化的隐藏语义缺陷由 Primary 审查。该建议不是已经修改产品范围或缩减当前失败分母。

若要继续更宽的自主能力，需另立明确的架构/模型适配对照，而非无限增补提醒。现有隐藏/合法 Reviewer 对照、完整多单元链路、Primary-only 成本基线与未见题资格仍未完成。两项外部冻结来源漂移回归仍排除，相关发布 gate 保持未满足。

## 历史与成本

实验实现、测试和全部失败均保留在 `v13b1` / `v13b2` 快照；工作 runtime 保持已接受的 `v13g`，未推广实验字段。没有修改只读兄弟仓库、commit 或 push。

第二批实际角色调用为 Coder 8 次、Reviewer 1 次、Explorer/Coordinator 0 次。未调用不算成功；Reviewer 的一次普通实现审查不能替代 hidden/clean 能力检验。

云端 tokens 与 Primary 主动耗时未知，不能宣布节省成本。Weekly used 约 22% 只用于预算控制；本次因形成阶段决策停止，而非耗尽 40% 上限。

## 后续确定性修复：静态诊断覆盖

继续核查执行轨迹确认：no-op 替换的模型载荷确实相同，没有发现编辑工具改变了模型意图。另发现 focused tests 失败会隐藏同时存在的 Ruff 错误；已增加可信 profile 的单命令 opt-in 诊断执行，默认行为和验收门槛不变。

该修复经过真实失败 pytest + F821 案例、九类边界验证、独立高风险审查和最终回归（539 passed、43 subtests passed、两项历史排除）。首次审查因引用范围不合法失败，保留后通过更窄的引用导航完成第二次审查，没有增加轮数或代填 verdict。

用法与权限边界见 [失败测试后的静态诊断](validation-diagnostics.md)。完整记录为 `benchmarks/work/capability-fit/conclusion-v13-diagnostics-1.json`。这不是第三个提示候选，也不改变上面的阶段 B 或 v2.1 决策；更完整的证据是否改善模型修复率，仍未实测。
