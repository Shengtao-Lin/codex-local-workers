# Coder harness：上下文 × 输出格式对照与迁移结论

日期：2026-10-12。阶段：`harness-factorial-20261012-1`。

## 决策

停止本批次，已有可核查结论；不放行产品、不放行新的 Coordinator 任务族。

当前 Qwen 可以完成被冻结的 E501 修复，并能写对新的单函数行为。
但严格迁移门槛为 **0/4**：单函数两次卡在机械格式，跨文件两次仍有语义错误。
不能再把这些失败统称为“模型完全不会写代码”，也不能把单例 3/3 当成系统稳定。

本轮没有修改生产 runtime、模型、Reviewer 候选或原有失败记录；没有 commit/push。
这是独立诊断提案 harness，不是正式 `local-unit` 完整链，也没有生成正式 Reviewer 验收。

## 先修实验

旧 `harness_repair_comparison.py` 的 full 组只在第一次请求附加修复上下文，
后续请求丢失这段内容，且旧 packet 仍以“新增 get_many”为目标。
后续验证会重新暴露 E501，因此不能说上下文丢失是唯一原因；但旧两组 0/3
不再作为公平对照的因果证据。历史全部保留，不改判。

新实验每次从固定任务、完整不变量、当前源码/hash 和最新反馈重建请求。
原十条行为测试字节不变，新增重复定义保护，避免旧的按名称建字典的 AST 比较漏掉重复方法。
这是新的验收版本，不追溯修改旧批次。

前置控制首次 17 passed / 2 failed，发现 raw-code 解析器 `.strip()` 损坏首行缩进。
在任何 live 调用之前改为只剥离换行，第二次 **19 passed**；旧源码及两次测试日志保留。
已知正确修复通过 11 项测试及全部静态检查；旧重复定义草稿被负控拒绝。

另有一次实验基础设施事故：首个 live case 的提案摘要与验证结果争用 `attempt-1.json`。
模型响应、实际编辑及检查结果均已保存。仅用外层收集器把提案记录改写到 `proposal-N.json`，
检查不覆盖保护；冻结驱动、模型消息、验收和预算不变。
首例未重调模型，核对实际编辑后独立重验并恢复结果，原始耗时标为未知。
因此本批次不能宣称基础设施零故障。

## 固定四组对照

同一 `MlflowTraceSource.get_many` 草稿、同一合同及 11 项验收测试，
同一 Qwen、采样和上下文上限，最多三次提案；每组独立三次，交错顺序预先冻结。
全部组均由宿主执行验证；没有自动格式化或 Primary 中途修代码。

| 上下文 | 输出 | 全检查通过 | 首次通过 | 模型请求总数 |
| --- | --- | --- | --- | --- |
| 精简：目标方法、完整合同、依赖事实 | 原始函数代码 | 3/3 | 3/3 | 3 |
| 精简 | JSON 精确替换 | 3/3 | 3/3 | 3 |
| 完整：额外加入整文件和只读上下文 | 原始函数代码 | 0/3 | 0/3 | 9 |
| 完整 | JSON 精确替换 | 3/3 | 3/3 | 3 |

通过须同时满足 pytest、Ruff format、Ruff lint、严格 Pyright 及保护文件未变。
full-code 的三次运行均重复提出无变化代码，非真实修复。

结论是**上下文与输出格式存在交互**，不是“JSON 导致失败”或“给更多上下文一定更好”。
三个重复只覆盖一个具体修复，不能估计一般任务成功率。
所有新组共同改变了任务持续性、任务表述及函数级宿主执行方式；与旧实验相比的改善
不能全部归因于上下文长度或输出格式中的某一个因素。

按预注册顺序选择：3/3 → 首次通过 → 调用次数 → 实际输入 tokens。
minimal-json 输入总计 2649，minimal-code 2655，full-json 19035。
选择 minimal-json 进入迁移只是遵循规则，**每次相差两个 tokens 没有实质经济优势**。

## 冻结真实切片迁移

从兄弟仓库复制真实源码、依赖类型和项目检查配置到本仓库隔离目录。
新增行为是实验合同，不是在宣称兄弟项目本身有相同 bug。
每项两次，固定顺序及最多三次提案，不调整模型或中途指导；先验证已知正确实现和负控。
两种任务的正确 witness 分别通过 9/9、15/15 及全部静态检查，未提供给模型。

| 任务 | 原始全检查通过 | 行为结果 | 主要残留 |
| --- | --- | --- | --- |
| 遍历 assistant 输出，识别非空白 TextPart | 0/2 | 两次均 9/9 | 空行含空格；后两次提案无变化，format 未过 |
| 关键词评分归一化，与复用 key 保持同一语义 | 0/2 | 两次均 12/15 | cache key 的三条一致性测试失败 |

跨文件第一例把 Pydantic Expectations 当成可用成员运算的容器，且缺少 scorer 限定；
最后提案使用旧 hash 被拒绝。第二例最后撤回整个 key 函数修改，只留下评分变化。
这说明还存在类型使用、跨文件不变量和修复回合控制问题。

迁移同时把单目标编解码器扩展为多个已命名函数/文件，但仍保留三个提案的单元预算。
一个提案只能修改一个块，因此多文件工作剩余修复机会更少；失败不能完全归因于模型本身。
本轮没有通过加预算挽救结果，也没有证明多文件任务永远不可用。

### 格式化反事实诊断，不改原分数

整批结束后另复制四个最终草稿，仅对授权文件运行 Ruff formatter，不再调用模型。
格式化前后 Python AST 完全相同：

- 单函数两例都变为 9/9 + 全部静态检查通过。
- 跨文件两例仍有三个失败，第一例仍有 Pyright 错误。

这是宿主辅助诊断的 2/4，不是原候选的 2/4；原迁移结果仍然 **0/4**。
它证明格式工作可以由确定性工具处理，但不能证明语义问题能被格式化解决。

生产 `worker-runtime.py` 已有 `_try_autoformat`，不需要另造一个 formatter。
不过 trailing-whitespace 可能先命中 diff-quality gate；相关
`autoformat_on_diff_whitespace` 分支是显式启用项，不能假定当前运行会自动修好。
本诊断仅执行严格检查，没有测试这些生产路径的接入效果。

## 下一步边界：建议，尚未实施

1. 不整体重写 harness，也不继续向提示堆规则。保留 scope/hash、不可变验收、归档和 Reviewer 门槛。
2. 单独冻结一个**单函数正式入口候选**：持续携带当前任务和紧凑相关上下文，
   复用已有的授权文件格式化流程，并核对它在 diff gate 前后的实际执行路径。
   格式化必须更新文件版本、使旧验证失效、重跑全部检查，不得放宽 lint。
3. 先做越界、并发文件变化、格式化失败、旧验证失效等负控；再对上述单函数任务和原修复任务
   跑固定重复批次，最后走正式 Reviewer。诊断通过不得跳过完整链验收。
4. 跨文件缓存一致性任务暂归 Primary，不加入新的 Coordinator 合格任务族。
   将来单独研究真实类型定义/依赖证据、每文件版本处理和两文件原子提案或合理预算，
   必须另立候选，不能混进单函数候选再事后解释。

这条路径检验的是“确定性工作交给宿主、模型专注受限语义编辑”能否在正常入口兑现，
不是把安全门槛删掉，也不是承诺更换 harness 就能消除模型能力限制。
