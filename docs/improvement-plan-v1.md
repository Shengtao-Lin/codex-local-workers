# Codex Local Workers — Improvement Plan V1

日期：2026-09-21
状态：供 Codex 实施前评审与逐步落地
适用范围：Python 项目、LM Studio、本地 Explorer/Coder、Codex Primary

## 1. 目的与使用方式

本计划基于上传的《Local Python Agent Orchestration Kit》设计文档，以及随后两轮架构和用量优化讨论。目标是在保持验收质量的前提下，降低每个最终通过验收的任务所消耗的 Codex usage。

这是对现有设计的修改建议，不表示已经检查或验证了实际 runtime 源码。实施时应先核对现有代码，保留已经正确实现的部分，并针对实际缺口修改，避免整套重写。

最终质量由固定的验收标准、可追溯的执行证据和 Primary 独立审查衡量。模型数量、测试通过数量和 worker 自述都不能单独证明质量。

### 1.1 核心决策

- 保留 Codex 负责架构、计划、关键决策和最终验收的分工。
- 保留 Qwen 负责一个完整工作单元的实现、测试和有限修复。
- 保留 gpt-oss 负责按需仓库探索。
- V1 暂不增加第三个本地模型，也不默认增加本地 reviewer。
- V1 不依赖额外开源 skills；先使用简短项目规则，工作流稳定后再考虑自定义协作 skill。
- 由 Python runtime 完成确定性校验、命令执行、状态记录和限制检查。
- 同一仓库一次只允许一个受本工具管理的写入 worker。
- 采用项目内可复制的工具目录；Python 为核心入口，PowerShell 只是 Windows 包装层。
- 第一版由当前 Codex 会话驱动 worker。runtime 不需要再调用 Codex API，也不需要实现独立的云端模型调度器。

### 1.2 保留的现有设计

| 已有设计 | 保留原因 |
| --- | --- |
| Primary 定义 WHAT / WHERE / 验收条件，Coder 决定 HOW | 给本地模型明确边界，同时保留实现空间 |
| Explorer 只读、Coder 使用受限工具 | 降低意外操作的范围，便于审计 |
| 写入前检查读取时的 SHA-256 | 防止直接覆盖已变化的文件 |
| 最后一次写入后必须重新验证 | 避免拿旧测试结果为新代码背书 |
| runtime 记录命令、退出码和测试结果 | 不依赖模型自行声称测试通过 |
| worker success 只是候选结果 | 保留 Primary 最终验收 |
| 不根据任务总调用次数机械 fallback | 允许复杂任务在持续取得进展时继续 |
| 一次调用可以多次读取、编辑、验证和修复 | 让 Qwen 完成有意义的实现工作 |

## 3. P0：修正权限边界与运行约束

### 3.1 编辑约束不等于进程隔离

删除原文中“approved unsandboxed/elevated 执行不会扩大 worker 权限，因为仍受 safe-edit 控制”的结论。

新的边界说明应包含：

- `SAFE_CREATE` / `SAFE_REPLACE` 限制的是 runtime 暴露的编辑接口。
- `VALIDATE` 中的 pytest 会执行测试、被导入的应用代码、conftest 和插件代码。[2]
- 这些代码可以产生不经过 safe-edit 的副作用，其权限取决于执行进程实际拥有的权限。
- 固定参数列表和 `shell=False` 可以避免 shell 字符串执行，并不能把任意 Python 测试变成受限程序。
- V1 明确面向可信本地仓库，提供操作约束和变更检查，不宣称实现操作系统级安全沙箱。
- 若后续要运行不可信代码，再单独设计进程、文件系统、网络和凭证隔离；不把这一能力暗含在 V1 中。

遇到 PermissionError 或 Access is denied 时，应返回环境阻塞原因和失败命令，由 Primary 根据实际宿主规则决定处理方式。runtime 不应自动提权，也不能把所有权限错误都归因于沙箱。

### 3.2 路径和写入规则

保留精确白名单、单一匹配、读取哈希、BOM 和换行风格保护，并补充：

- READ、SEARCH、LIST 同样需要明确的可访问目录和排除目录。
- 分别定义读取范围与写入范围；允许读取必要的调用方、接口和相邻测试，不因此扩大写权限。
- 对路径做规范化与实际目标检查；处理符号链接、Windows junction、大小写和路径别名，不能仅检查字符串中是否包含 `..`。
- V1 可直接拒绝经过符号链接/junction 的编辑目标，以减少实现复杂度。
- 正在执行的 runtime 源码、控制文件、packet、日志、验证记录和任务状态不加入 Coder 的写入白名单。
- 在受管理的写入锁下完成哈希检查和写入，采用原子替换；新建文件不得覆盖已有文件。
- 运行锁只能协调本工具的调用，不能保证外部编辑器不会写入；发现外部变化时使相关结果失效并报告冲突。

以上检查降低意外错误风险，不应描述为能抵御具有同等宿主权限的恶意测试进程。

### 3.3 环境与执行

- Python 解释器、工作目录和测试配置来自可信的项目配置，worker 只请求执行既定验证流程。
- 不硬编码所有项目都使用 `.venv/Scripts/python.exe`；Windows 可将其作为可配置默认值。
- 预检解释器、pytest、模型端点以及已配置的检查工具；缺失时返回明确阻塞信息。
- 不在 worker 循环中安装依赖、创建环境或修改机器配置。
- 保留原有每次调用的 turns、repair 和 protocol error 限制，并将其放入配置。
- 增加 LM Studio 请求超时、整次调用期限、工具输出上限和取消处理。
- 命令超时后清理受管理的子进程树；若不能确认已结束，应报告不确定状态并阻止新写入调用，避免后台进程继续改文件。
- 输出截断必须显式标记，完整日志按策略保留。超大输出不能无限占用内存，也不能静默丢失失败证据。

原有 16/24 turns、2 次 repair、180 秒命令超时可作为起点。新增请求期限和整次调用期限应根据本机推理速度设置，不把这些默认值当作模型能力结论。

## 4. P0：统一 packet 和工作状态

### 4.1 区分指令与事实

原文把用户需求、packet、feedback、仓库状态和 memory 放入同一个“权威顺序”，容易混淆两个问题。

- 执行指令：在宿主权限与仓库约束内，由用户需求和 Primary 当前批准的 packet 定义工作。
- 实际事实：仓库内容、实际变更、命令记录和测试结果用于判断当前状态。
- 历史笔记：memory 和 worker 总结提供背景，不覆盖当前指令，也不覆盖当前文件事实。

Primary 的新反馈应合并为新版本 packet。worker 不需要同时解释互相冲突的旧 packet 和最新反馈；验收标准有意改变时必须记录原因和版本变化。

### 4.2 packet 最小增补

| 字段 | 目的 |
| --- | --- |
| `schema_version` | 新协议可显式升级到 2，旧协议通过兼容转换或明确报错处理 |
| `task_id` | 顶层用户任务身份 |
| `unit_id` | 稳定的逻辑工作单元身份；不能靠改名刷新失败历史 |
| `plan_revision` / `packet_revision` | 区分计划调整和本次执行说明调整 |
| `run_id` / `attempt` | 标识实际调用；由 runtime 校验唯一性并归档最终 packet |
| `scope.read` / `scope.modify` / `scope.create` | 分开表达读取与写入权限 |
| `scope.forbidden` | 对所有相关操作生效的明确排除范围 |
| `required_behavior` / `acceptance_criteria` | 为每项标准分配稳定 ID，便于引用和审查 |
| `validation_profile` / `focused_tests` | 选择可信配置中定义的验证流程，不接受任意 shell 字符串 |
| `review_feedback` | 已整合到当前执行说明中的具体问题列表 |
| `memory_refs` / `evidence_refs` | 指向本次任务真正相关的决策与文件证据 |
| `limits` | 单次调用的工具、模型、输出和时间边界 |

scope、测试目标和 profile 在 worker 启动前由 runtime 验证。验收条件原文、已验收设计决定和当前 packet 都不由 worker 修改。

一次 packet 应覆盖一个完整、可测试的行为。不要为了减少单次改动，把一个小功能拆成许多需要 Codex 分别审查的微步骤。

### 4.3 增加 BLOCKED 与范围扩展出口

保留现有工具动作，增加 `FINISH_BLOCKED`，或为终止动作增加等价的结构化状态。

```json
{
  "status": "blocked",
  "reason_code": "needs_scope_expansion",
  "requested_scope": {
    "read": ["src/jobs/queue.py"],
    "modify": ["src/jobs/queue.py"]
  },
  "reason": "The required ownership check is implemented in this module.",
  "evidence_refs": ["evidence-07"],
  "proposed_next_step": "Primary reviews the scope and issues a revised packet."
}
```

请求扩展范围不会自动授权访问或修改。Primary 可以批准新版 packet、重新拆分任务，或接管。

### 4.4 runtime 结果与 Primary 决策分开

| runtime 结果 | 含义 |
| --- | --- |
| `ready_for_review` | 本次所要求的自动检查完成且通过，等待 Primary 审查 |
| `blocked` | 范围、依赖、环境、需求或状态冲突使工作无法继续 |
| `failed` | 在允许范围和预算内未达到本次自动质量门 |
| `interrupted` | 用户取消、进程中断或运行期限到达，需说明遗留状态 |
| `policy_violation` | 发生未经允许的操作请求或检测到越界变化，停止并报告 |

Primary 另行记录 `accept`、`rework`、`replan` 或 `takeover`。`next step` 是验收后的计划推进，不混作 worker 成功状态。

`FINISH_SUCCESS` 可以保留为兼容动作名，但应映射到 `ready_for_review`，不能把整个工作单元直接标记为 accepted。

## 5. P0：修正重试、进展和接管策略

### 5.1 失败分类

| 类别 | 示例 | 处理 |
| --- | --- | --- |
| 实现失败 | 断言不满足、类型错误、遗漏要求 | Qwen 在当前预算内修复；耗尽后交 Primary |
| 协议失败 | 无效 JSON、未知动作、参数不合法 | runtime 返回精确错误；超过单次阈值结束调用 |
| 范围/计划阻塞 | 必须修改未授权文件、接口定义矛盾 | 返回 BLOCKED，等待 Primary 更新计划 |
| 环境阻塞 | 端点不可用、缺依赖、解释器无权限 | 独立统计；避免通过反复改代码处理环境问题 |
| 状态冲突 | 读取后文件被外部修改、已有 worker 正在写入 | 停止写入，重新核实基线 |
| 越界/危险操作 | 未授权路径、试图修改控制文件 | 立即停止并交 Primary，不自动扩权 |

环境失败不计为“Coder 不能实现需求”，但仍消耗时间，必须计入端到端实验成本。环境重试也应有限，连续故障时返回阻塞，不无限等待。

### 5.2 保留两类历史

- 当前方案的失败 streak：用于识别同一策略是否反复失败。
- 同一逻辑工作单元的未解决问题记录：跨 packet revision 保留，用来发现改名、改措辞或切方案后仍没有解决原问题。

更新 packet、获得新证据、修改方法可以开始新尝试，但不能自动删除未解决问题。合法拆分工作单元时记录父子关系，并保留问题归属。

禁止把无关的新证据、测试数量变化或更换 `unit_id` 直接当作实现进展。

### 5.3 进展的判定

runtime 记录客观变化，由 Primary 在审查点确认是否取得实质进展。可接受的依据包括：

- 某个原先未满足的验收条件现已通过对应验证。
- 在相关测试未被删除、跳过或弱化的前提下，已知失败被修复，且没有相应回归。
- Explorer 提供了能改变当前决策或解除当前阻塞的新证据；这不自动清零 Coder 的实现失败记录。
- Primary 验收了一个明确的子行为。

`failure_signature` 应尽量包含阶段、稳定测试标识、异常类型或规则标识。归一化时间戳、临时路径和随机 ID，并保留原始错误供核查；文本签名不是故障根因的证明。

### 5.4 fallback 行为

保留“相同失败、无进展或同一质量门连续失败约 3 次时交 Primary”的默认策略，同时明确计数所属的 worker、unit 和质量门。

- 原有 `max_local_repairs=2` 表示首次验证失败后最多进行两轮修复，不是最多编辑两次。
- 内部 repair 和 Primary 发起的新调用分别计数，避免重复累计一次失败。
- 每次重试应有明确变化：补证据、缩小范围、修正方案或具体反馈。
- task 总调用次数仅作统计，不成为唯一 fallback 条件。
- 运行预算到期表示应暂停并报告进度，不等价于模型能力失败。
- 接管时附未解决问题、已有有效改动、未验收改动和最新验证记录，减少 Primary 重新调查的成本。

## 6. P0：基线、验证与恢复

### 6.1 调用前基线

runtime 在实际写入前记录：仓库标识、当前 HEAD（如适用）、已有 tracked/untracked 改动、允许写入文件的内容哈希，以及本次读取和验证涉及的关键输入。

不得要求自动清理用户工作区，也不得用 `git reset --hard` 或 `git clean` 作为失败恢复流程。可以在有用户改动的工作区执行，但必须能识别并保护已有内容；无法可靠归因时返回阻塞。

调用后变更清单需明确包含新建文件。普通 `git diff` 不包含所有 untracked 内容，不能作为唯一审查来源。

### 6.2 验证绑定实际代码状态

- 编译检查覆盖本次修改和新建的 Python 文件。
- `py_compile` 会生成字节码文件；将输出放入受管理的临时目录，或采用不落盘的语法编译检查，不把这些副产物误判为业务代码越界。[3]
- 通过语法检查后执行既定 focused tests；按项目已有配置选择必要的 lint/type checks，不擅自加工具或改规则。
- 记录命令参数、解释器、工作目录、起止时间、退出码、测试统计、日志位置和检查时的输入状态。
- 验证前后检查相关源文件、测试与配置是否变化。测试过程中或之后发生相关写入，应使结果失效。
- 零测试收集、关键测试全被 skip/xfail 或无法确认规定测试执行时，不得仅凭退出码 0 宣称通过所要求的质量门。
- 不能仅检查“worker 最后一次编辑时间”；还要考虑外部编辑和测试自身产生的修改。
- 显式记录检查覆盖范围；文件哈希可以证明记录对应哪些内容，不能证明已捕获全部动态依赖。

语法检查通过不代表运行时正确；focused tests 通过不代表整个功能验收完成。

### 6.3 Primary 审查与验证复用

Primary 检查实际变更、必要的上下文、调用方与测试，逐项对应原始验收条件，并执行相关的更广泛验证。

对于相同代码状态、相同环境下已由可信 runtime 执行的机械检查，不要求 Primary 再逐条重复。把新增验证用于行为边界、集成和回归风险；状态、环境或证据不匹配时重新执行。

### 6.4 失败和中断后的状态

失败不意味着工作区自动恢复。handoff 必须列出已写入、未验收和验证失效的文件。下一次调用先确认是否继续这些改动。

runtime 可保存授权文件的调用前内容以便恢复，但 V1 不自动回滚有外部变化的文件。需要恢复时只处理可准确归因的内容，并检查当前哈希，保护用户后续修改。

## 7. P0：Task memory 与 handoff 的归属

### 7.1 memory 需要记录任务本身

在已有 usage、streaks、recent_attempts 基础上补充：

| 内容 | 最少信息 | 写入责任 |
| --- | --- | --- |
| 任务目标与约束 | 原始目标、范围、不可改变的行为 | Primary |
| implementation plan | 稳定 unit ID、依赖、状态、当前步骤 | Primary |
| accepted decisions | 已确定接口、设计理由、适用范围 | Primary |
| completed units | 已验收步骤、对应 run 和代码证据 | Primary |
| open issues | 未解决问题、归属 unit、阻塞原因 | Primary 维护结论；runtime 追加事实 |
| execution history | 调用、动作、错误、验证和耗时 | runtime |
| worker proposals | 实现解释、建议、疑问 | runtime 单独保存 worker 提交的内容 |

控制文件通过 runtime 的受管理入口更新，避免 Primary 和 runtime 同时直接覆盖同一个 JSON。Primary 是决策的作者，runtime 是写入和归档的执行者。

每次调用只给 worker 当前 unit 所需的 memory 摘要与可读取证据，不把整个历史重复注入。

### 7.2 运行记录

每个 run 保存最终 packet、调用前基线、工具事件、实际变更、验证记录和 handoff。终止后的执行记录不再覆盖；Primary 的后续 review 单独追加。

`current-task.json` 和 `last-*` 可以作为指针或可重建摘要，不能成为唯一历史。状态更新采用锁和原子写入；中断恢复先检查实际工作区，再决定能否继续。

### 7.3 handoff 区分事实与解释

建议至少分成以下部分：

- `identity`：task、unit、run、packet revision。
- `runtime_facts`：读取/写入清单、基线与当前状态、执行命令、退出码、验证结果、限制触发情况。
- `worker_claims`：实现解释、对验收条件的自评、未解决疑问；明确属于待核实内容。
- `evidence_refs`：文件路径、读取范围、读取时哈希、日志和 diff 位置。
- `next_action_required`：是否需要审查、范围调整、环境处理或接管。
- `primary_review`：由 Primary 后续记录，worker 不得填入 accepted。

Explorer 的关键结论要引用实际读取的文件范围和版本；“读过这个文件”只说明有来源，不保证结论正确。runtime 可校验引用合法性，语义正确性仍由 Primary 核查。

## 8. P1：直接降低 Codex usage 的改动

### 8.1 将完整的本地循环封装为一次调用

一次 Coder 调用内部完成读取、编辑、focused validation 和有限 repair。中途的正常测试失败不用逐次交给 Codex 决定；达到 ready_for_review、blocked 或调用限制时再返回。

不要把 Qwen 的每个工具动作包装成一次需要 Codex 决策的外层调用。进度可由 runtime 提供简短状态；原始工具交互留在本地日志。

### 8.2 简明 handoff 与按需证据

给 Codex 的默认摘要可先以约 500–1,000 tokens 为软目标，包含：行为变化、文件列表、验收项结果、验证摘要、阻塞和证据入口。

这个目标不是截断正确性信息的硬限制。失败、证据缺失和输出截断必须显式保留。完整 diff、代码、命令和日志始终可按需读取。

事实字段由 runtime 生成，避免额外调用云端模型来总结每轮日志。worker 的解释不与 runtime 事实混写。审查中优先读取实际变更和有关上下文；发现证据不足时再扩展阅读范围。

### 8.3 按任务选择路径

| 任务情况 | 建议路径 |
| --- | --- |
| 极小、明确、位置已知的修改 | Primary 直接完成；记录使用直接路径 |
| 实现边界明确，相关文件已知 | Primary packet → Qwen → runtime 验证 → Primary 审查 |
| 调用链或影响范围不清楚 | Explorer → Primary packet → Qwen → 审查 |
| 涉及关键接口、事务、并发或架构冲突 | Primary 先明确方案与不变量，再决定下放范围 |
| 环境未准备好 | runtime preflight → blocked；不要进入代码修复循环 |

路由由少量明确规则与 Primary 判断完成，不额外增加一个模型 router。不要强制每个任务都使用 Explorer，也不要默认增加 reviewer。

### 8.4 预先固定关键验收场景

Primary 在实现前确定：正常路径、核心异常路径、必须保持的状态或接口，以及需要验证的边界。

以原文 lease fencing 场景为例，至少考虑有效 worker 的正常完成、失去 lease 后拒绝提交成功、失去 lease 后拒绝提交失败，以及真正提交结果时的所有权检查。具体并发语义需依据实际仓库核实，不能只按函数名推断实现位置。

Qwen 可以实现回归测试和增加场景，但不得为了通过检查自行删掉、skip、放宽或替换预先批准的验收要求。现有测试确实需要随需求变更时，说明理由并交 Primary 更新 packet。

bug 修复尽可能验证新增测试在旧实现上失败、在新实现上通过。该比较由 runtime 或 Primary 在临时快照中完成，不授予 worker 任意 Git 操作权限，也不破坏用户当前工作区。

### 8.5 缓存有效证据，控制常驻上下文

- 保存简短 repo map：入口、模块职责、关键接口、相关测试和验证命令。
- 每条可复用发现携带来源与哈希；源文件变化后重新读取，新增/删除文件后刷新相关目录和搜索索引。
- 文件未变化也不代表所有关系仍有效；调用链缓存需要检查其依赖文件和相关结构变化。
- `AGENTS.md` 只保留稳定约束、路由规则、调用入口与验收职责；完整协议按需读取。
- 不把完整 worker 历史、所有 run 日志和整个计划常驻注入每次提示。
- 只启用当前工作所需的工具集和 MCP 连接；先测量实际上下文开销，不假设所有宿主的工具加载方式相同。

Codex 官方资料说明，用量受模型、上下文、推理、工具使用和缓存等因素影响，并建议减少无关源材料和冗长的 AGENTS.md。[1] 本计划不承诺固定节省百分比，也不把 tokens 或调用次数直接等同于套餐额度。

## 9. 是否需要开源 skills

### 9.1 V1 的建议

通用 Python 设计、编码和代码审查，先使用 Codex 本体。V1 不把安装第三方 skill 集合作为前置条件。

项目仍然需要自己的 worker runtime、明确的 packet 和验收流程；这些由实现代码提供。Codex 本体也不会自动知道本项目的 LM Studio 调用协议，因此应给它一份简短的项目协作规则和可调用入口。

先在 AGENTS.md 与按需读取的协议文档中表达这些规则。工作流稳定后，如果确实需要跨项目复用，再考虑封装成一个自定义 `local-python-orchestration` skill。

### 9.2 区分各层职责

| 层 | 在本项目中的作用 | 不能替代的内容 |
| --- | --- | --- |
| 模型 | 理解需求、推理、生成实现、判断结果 | 确定性校验和真实执行证据 |
| Skill | 可复用的操作说明、参考资料及可选脚本 | 宿主权限与 runtime 的强制边界 |
| AGENTS.md | 项目稳定约束、入口和协作规则 | 每次任务的详细 packet 与完整历史 |
| Tool | 实际执行 READ、SEARCH、SAFE_REPLACE、VALIDATE | 任务规划和最终验收 |
| Runtime | 工具分发、白名单、状态、限额、执行与记录 | 完整操作系统隔离和所有语义判断 |
| Test / lint / type check | 可执行的行为与规则验证 | 对需求完整性和设计合理性的审查 |

Codex 的 skill 可以包含指令、参考资料和可选脚本，并按需加载完整说明。[4] 将 skill 装到 Codex，并不意味着通过 LM Studio 直接调用的 Qwen/gpt-oss 自动获得同样的说明、工具或 memory。这是当前自定义 runtime 的集成责任。

### 9.3 可选的自定义 orchestration skill

若后续封装，建议只承担以下内容：

1. 判断当前任务是否值得委派，以及是否需要 Explorer。
2. 按 schema 准备 packet，并调用已有 Python CLI。
3. 读取简明 handoff，按需查实际 diff 和证据。
4. 给出 accept/rework/replan/takeover，并更新任务状态。

skill 不复制 runtime 的状态机，不自己实现另一套重试计数，也不授权 worker 提权、扩范围或使用任意 shell。技能说明保持精简，详细 schema 通过参考文件提供。

Qwen 与 Explorer 先使用 runtime 显式加载的短角色说明和当前 packet，不需要在 V1 建立通用 skill discovery 或 skill marketplace 支持。

### 9.4 什么时候才引入外部 skill

出现可重复观察的缺口时再选择，例如某种项目框架的测试约定总被遗漏，或某类调试流程反复浪费 Primary 的时间。

候选 skill 应能回答：解决哪个具体问题、何时触发、依赖哪些工具、会增加哪些阅读和调用、是否与现有权限和 packet 冲突。若附带脚本，先检查其行为和来源；保留采用的版本与必要许可信息。

采用前后用相同任务做小规模对比。如果只有更长的计划、更频繁的审查或更多工具调用，而没有降低返工和缺陷，就不保留。通用规划、测试或审查 skill 的存在，不是必须安装它们的理由。

## 10. 项目布局与配置

保留现有 `.local-agents/` 工具目录、`.agent/` 状态目录和根目录 AGENTS.md。以下是建议的职责划分，已有等价文件可继续使用。

| 路径 | 用途 |
| --- | --- |
| `AGENTS.md` | 简短协作规则与调用入口 |
| `.local-agents/config.json` | 端点、模型映射、解释器、限额和验证 profiles |
| `.local-agents/local-explore.py` | Python Explorer 入口；可由薄包装调用现有实现 |
| `.local-agents/local-code.py` | Python Coder 入口 |

| `.local-agents/safe-edit.py` / `task-policy.py` | 编辑与策略执行；避免重复实现同一规则 |
| `.local-agents/protocol.md` | 按需读取的 packet、动作与 handoff 说明 |

| `.agent/current-task.json` | 当前任务指针或可重建摘要 |

`.agent/` 是本项目自定义运行状态目录；`.agents/skills/` 是可选 Codex skill 的项目位置，两者职责不同。[4]

配置中将 `explorer_model`、`coder_model` 和可选 `reviewer_model` 按角色映射到 LM Studio 的实际模型 ID；默认复用当前 gpt-oss 与 Qwen。模型 ID 必须从本机配置核实，不把展示名称当作通用 API ID。

状态、日志和机器专属配置按项目规则忽略；可提交不含凭证的示例配置。若端点要求凭证，使用环境变量，不写入 packet、日志或 Git。

示意入口如下，具体参数以实施后的 CLI 为准：

```powershell
python .local-agents/local-explore.py --task "Trace the lease completion path"
python .local-agents/local-code.py --packet .agent/implementation-packet.json
```

更新原文所有调用示例，消除项目内目录与 `$env:USERPROFILE/.codex/local-workers/` 全局路径混用。现有全局安装如需保留，可提供显式兼容入口，但不作为项目默认依赖。

## 11. 分阶段实施步骤

每个阶段先检查已有实现，列出实际缺口，再提交一个可审查的完整改动。不要把本计划中的每条建议都变成一次独立的 Primary 调用。

工具自身的修补先由 Primary 直接实施。若使用本地模型辅助修改 runtime，应在独立副本中将其作为普通待开发项目处理，由可信的外部执行器验证；不让正在运行的 worker 修改自己的校验器和权限规则。

| 阶段 | 实施内容 | 验收出口 |
| --- | --- | --- |
| S0：核对现状 | 检查现有脚本、配置、协议、测试与调用路径；记录已实现/部分实现/缺失 | 有基于实际代码的差异清单，不进行无理由重写 |
| S1：协议与预检 | unit/revision、状态、BLOCKED、反馈合并、统一入口、环境预检 | 缺依赖、错误配置、范围不足可以明确结束，不进入错误修复循环 |
| S2：写入与执行边界 | 路径检查、写入锁、哈希保护、超时、中断、权限说明 | 越界/冲突被拒绝；中断后的进程和文件状态可解释 |
| S3：验证与记录 | 调用前基线、新建文件处理、验证状态绑定、memory 归档、重试策略 | 成功、返工、失败、接管均可追溯；不能用旧结果验收新代码 |
| S4：省用量流程 | 完整本地循环、精简 handoff、按需探索、验收场景和证据缓存 | Codex 不需要读取正常情况下的全部 worker 过程 |
| S5：基线实验 | 按第 13 节比较直接 Codex 与混合流程 | 得到实测用量、质量、耗时及失败分布 |
| S6：可选实验 | 按瓶颈试验本地 reviewer、自定义 skill 或替换模型 | 单独验证收益，可关闭，可恢复原配置 |

第一个真实任务选择范围明确、涉及少量源文件和 focused tests 的 Python bug 修复。先跑通一次成功和一次需要返工的闭环，再扩大任务复杂度。

## 12. 必须覆盖的验收案例

测试重点是可能破坏边界、记录真实性或恢复行为的地方，不为每条文档说明都编写镜像测试。失败路径可用可控的模型响应或假进程模拟；真实模型验证留给端到端试跑。

| 场景 | 必须观察到的结果 |
| --- | --- |
| 正常实现并通过 focused tests | 返回 ready_for_review，Primary 审查后才 accepted |
| 首次测试失败，local repair 成功 | 中间过程在本地结束；最终 handoff 保留必要记录 |
| 需要未授权文件 | 返回 scope expansion 请求，文件未被自动修改 |
| 非法路径、符号链接/junction 越界 | runtime 拒绝访问或编辑，不能只靠提示词阻止 |
| READ 后外部修改文件 | 拒绝旧哈希写入，不覆盖外部内容 |
| 原工作区已有用户改动 | 变更清单可区分已有内容和本次改动 |
| 新建 Python 文件 | 文件出现在变更清单、语法检查和 Primary 审查中 |
| 验证后再写代码或测试 | 原验证记录失效，不能成功结束 |
| 测试为零或关键场景被跳过 | 不把退出码 0 直接作为验收通过 |
| 修改 packet 但同一问题仍失败 | 未解决问题记录保留，必要时触发 Primary 决策 |
| 模型端点断开或缺依赖 | 分类为环境阻塞，不循环修改业务代码 |
| 请求超时、测试挂起或用户中断 | 有限结束，报告遗留修改和进程状态 |
| 运行两次或中断后恢复 | 旧 run 证据仍存在，新调用先核对实际状态 |
| Explorer 引用未读或已变化的文件 | 引用被拒绝或标记失效，不形成合格证据 |
| 本地 reviewer/skill 未启用 | 主要闭环仍能完整工作 |

## 13. 用量与质量基线实验

### 13.1 实验设置

选约 10 个有代表性的历史或自建 Python 任务作为第一轮试跑，包含小 bug、跨函数行为、异常路径、测试补充和小型重构。这个规模用于发现瓶颈，不用于宣称普遍性能结论。

- A：Codex 直接探索、实现和验收。
- B：本计划中的混合流程，按任务选择是否使用 Explorer；默认无本地 reviewer。
- C：仅在 B 的瓶颈支持时，单独测试 B 加本地预审或某个 skill，一次只改变一个主要变量。

每组从相同代码起点、相同依赖环境和相同用户要求开始，使用事先确定的验收场景；不同组不能继承对方已经写好的实现或提示。

记录模型 ID、量化版本、上下文/生成设置、硬件和工具配置。一次性工具开发成本与每任务运行成本分开报告，避免把建设成本隐去，也避免将其全部计入某个任务。

### 13.2 最小指标

| 指标 | 口径 |
| --- | --- |
| Codex 用量 | 优先使用实际可获取的用量数据；可用时记录 input/output/cached/reasoning tokens |
| 每个合格任务的平均用量 | 全部尝试、失败和接管的 Codex 消耗总和 ÷ 最终验收通过任务数；零通过时标记不可计算 |
| 验收通过率 | 使用相同标准，不能只看 worker 的成功率 |
| 初次审查通过率 | 首次提交即被 Primary 接受的比例 |
| 返工与接管 | 次数、原因、涉及的质量门 |
| 缺陷 | Primary 或后续固定验收发现的漏项、回归和错误 |
| 总耗时 | 包括模型加载、探索、实现、审查、失败和接管 |
| 用户干预 | 需要人工补环境、改范围或修复状态的次数 |

套餐额度、API tokens 和调用次数不是可直接互换的计量单位。[1] 如果只能使用额度面板，记录测量窗口和其他并行用量，明确结果是粗略估计；不要伪造精确节省比例。

### 13.3 如何决定下一步

| 实测问题 | 优先调整 |
| --- | --- |
| Primary 反复阅读大量内容 | 改 handoff、证据索引与审查上下文选择 |
| packet 很长，规划开销高 | 把稳定 schema/规则移到程序和参考文档，按完整行为分包 |
| Qwen 经常误解范围或要求 | 改 packet、验收场景和任务粒度 |
| 同类边界遗漏频繁出现 | 先补验收场景，再试验只读本地预审 |
| Explorer 的结论总要重新调查 | 改证据格式与探索范围，再比较是否替换 Explorer |
| 任务明确但 Qwen 仍反复实现失败 | 用失败样本比较替换 Coder，而非默认增加更多角色 |
| 模型切换/加载占用大量时间 | 比较由同一本地模型承担两个角色，或调整运行顺序 |
| 第三方 skill 增加步骤却不降低返工 | 关闭该 skill，保留真正有用的规则 |

质量门先保持一致，再比较效率。没有证据表明质量保持时，不以较低 usage 宣称方案成功。

## 14. 后续可选项与明确暂缓项

### 14.1 本地预审实验

默认关闭。优先复用现有 gpt-oss，或评估 Qwen 在独立上下文中的预审效果，不立即增加第三个本地模型。

输入为需求、验收条件、实际 diff 和必要代码，不附 Coder 的自我辩护。只读输出需包含问题位置、触发条件、证据与建议验证方式；不直接修改文件，也不替代 Primary。

### 14.2 V1 暂缓

- 多个写入 worker 并行操作同一仓库。
- 自动 commit/push、自动发布或无人值守跨任务调度。
- 通用多语言框架、skill marketplace、向量数据库和复杂 agent 编排依赖。
- 为了角色齐全而增加 planner、router、tester、critic 等独立模型。
- 用多个模型投票代替测试和 Primary 的最终判断。
- 在缺乏实测证据前承诺某个节省比例，或把固定默认限额作为普遍最优配置。
